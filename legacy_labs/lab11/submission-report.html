Recommendation: Among the four candidates, use {customer_id: "hashed"} when customer order history is the dominant access pattern. It balances distinct customers while allowing equality lookups to target a shard. Validate with real workload measurements: hashing does not distribute one customer's orders, and it sacrifices range locality.

MongoDB 5.0+ resharding overview

  1. Check cluster health, version compatibility, unique-index rules, globally unique _id values, collection features, active index builds, and available resources.
  2. Disable the balancer and issue reshardCollection through mongos, specifying the collection and new shard key.
  3. Monitor the operation through $currentOp. After completion, verify data, chunk placement, and application query plans; then re-enable the balancer.

Resharding copies data and catches up concurrent writes. Plan for high I/O/CPU, temporary extra storage, increased latency, and a brief write-blocking critical section. Unique indexes must satisfy shard-key requirements; duplicate _id values can cause failure, and queryable-encryption collections are unsupported. Only one collection resharding/move/unshard/rewrite operation runs at a time. Consult the version-specific MongoDB resharding documentation.

Lab 11.2 — Hotspot demonstration

The Compose lab inserted 10,000 documents into each collection on a two-shard MongoDB 7.0 cluster.

CollectionShard keyObserved per-shard countRange-query plan
hotspot_data{ts: 1}shard2RS: 10,000Date range targeted shard2RS (SINGLE_SHARD).
even_data{user_id: "hashed"}shard1RS: 4,970; shard2RS: 5,030Same date range scattered to both shards (SHARD_MERGE).

An equality query on the hashed user_id targeted one shard. A range query on that hashed field scattered to both shards. These plans were verified with explain(); per-shard counts were read with collStats.

Increasing timestamp values continually target the highest range chunk, which creates a write hotspot even if the collection can later be balanced. Hashed values distribute distinct keys across chunks, but lose ordered range locality. A ranged key remains appropriate when range queries are central and insertion rate or key design avoids a single active upper-bound chunk.
